# Opening Settings with Ctrl+Comma

Droidcast opened Settings in all four measured transitions on the Android 16 tablet. On both APKs, the input dispatcher sometimes reported a focused application with no focused window while switching activities. Each transition subsequently reached the General page. The intermittent no-focused-window ANR remains unexplained. [Issue #121](https://github.com/moikdev/droidcast/issues/121)

The historical failure stopped after three successful shortcut checks. The screenshot showed the palette. The subsequent hierarchy contained the system ANR dialog, Android reported an input-dispatch timeout, and the captured main-thread stack was in the message queue. The earlier broad run on that same APK had already passed the Settings step before encountering the separate typing discrepancy in #59. [Historical screenshot, hierarchy and stack](HTML-VIEWER-EVIDENCE.md#regression-checks)

## Holding Find after Settings Search gains focus

Settings now matches a handled navigation press by keyboard device, key code and original down time. It consumes repeats and the release even when the modifier is released first. The Settings window checks ownership before forwarding events to the input method. A fresh press can still type. Losing window focus or pausing the activity clears ownership.

On the API 36 tablet, three unmodified F repeats after Ctrl+F inserted `fff` on main at `573328a7`. ## Installed extension loading at activity startup

Settings and the palette both create a `PaletteStore`. Previously, its constructor opened the installed-extension directory and read and parsed each extension's Store metadata and command manifest on the UI thread. The initial directory scan now runs on the I/O dispatcher. Shortcuts and the Settings shortcut inspector wait for the installed inventory and app list before resolving a command. Store installation and removal await the initial scan. Installed and reviewed-text views can show loading while the inventory is pending.

On the dedicated API 36 emulator, a controlled application context supplied an isolated directory with one installed command to the production store. The instrumentation counted calls to obtain the catalog's files directory. It held the worker at that access and checked whether the UI could report loading while the command was still unavailable. After release, it checked the exact command title. These observations measure thread ownership and command readiness. Activity launch duration, real-world collections and the cause of the earlier ANR in #121 remain unmeasured.

### Alias field visibility with the keyboard open

The earlier tablet capture in #152 showed the upper shortcut inspector while the alias editor had focus. For #153 we tested whether the field could settle out of sight after opening Settings. The first three instrumentation builds used the same application APK (`42b6c947`). We exercised the palette’s Set alias action on a synthetic note, then a separate scenario in which a requested note became available after the disabled editor was placed. Both used the dedicated API 36 emulator in tablet and resized phone layouts at the default font scale.

Each scenario verified the requested command, field focus and the exact draft produced by an Android-injected X key. After focus, the opening probe sampled clipped and measured field dimensions and IME visibility for a settling interval of at least 1.6 seconds. The second fixture also hid and reopened the IME through the window controller and checked the field against the visible display frame. It deliberately scrolled the inspector through its Compose scroll action. The final fixture used a Compose-injected touch swipe and measured the scroll offset before and after the gesture and again after 350 ms.

| Final observations on both entry paths | Tablet | Phone layout |
| --- | --- | --- |
| Fully visible field height before typing and after entering x | 60 px | 105 px |
| Inspector offset before → after touch swipe | 194 → 0 px | 641 → 0 px |
| Visible field height after swipe | 0 px | 0 px |
| Focus, keyboard, target and draft after swipe | Retained | Retained |

The application kept the editor visible for typing without a test scroll to reveal it after focus. Scrolling it away deliberately produced a hidden field with focus retained, and the inspector stayed at the new position. These runs did not reproduce a field that settled hidden without a scroll. Physical keyboards, OEM IMEs, large fonts, orientation changes and draft persistence after saving are outside the coverage.
